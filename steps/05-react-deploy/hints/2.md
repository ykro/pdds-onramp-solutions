# Pista 2. Cliente tipado, estados explícitos y accesibilidad

Centraliza las llamadas al backend en un módulo `src/lib/api.ts` con tipos exactos para respuestas y errores. Mantén siempre los montos en centavos (`number` entero) hasta el momento de formatear el texto visible en pantalla.

Cada vista que consulta red debe modelar cuatro estados claros, sin pantallas en blanco ni errores silenciosos.

- Cargando (`aria-busy="true"` o indicador con `role="status"`).
- Error recuperable (mensaje claro con `role="alert"` y botón para reintentar).
- Vacío (texto que explica qué hacer cuando el carrito o el historial están vacíos).
- Contenido listo con botones nativos (`<button type="button">`) y `<label htmlFor="...">` en cada campo de formulario.

Para el deploy en Vercel y Neon, revisa que `VITE_API_URL` y las variables del backend vivan en la configuración del proyecto y que CORS permita únicamente el origen de tu frontend.

Si buscas comandos y verificaciones puntuales, abre [la pista 3](3.md).
