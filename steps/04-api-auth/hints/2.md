# Pista 2. Verificación JWT con JWKS local, roles e idempotencia

Distingue siempre entre autenticación (`401 Unauthorized`, cuando el token falta, venció o tiene firma inválida) y autorización (`403 Forbidden`, cuando el usuario está autenticado pero carece de permisos, como intentar llamar a `PATCH /api/products/{sku}/stock` sin figurar en `admins`).

Al validar JWT en `backend/tiendita/api/auth.py` con `PyJWT[crypto]` y `PyJWKClient`, fija explícitamente los algoritmos permitidos (`RS256` o `ES256`) y verifica `iss`, `aud` y `exp`. Las pruebas levantan un servidor JWKS local para que todo funcione sin crear todavía una cuenta de Neon.

En `GET /api/orders/mine` (`CA-4.4`), filtra siempre por `current_user.sub` dentro de `StoreService` para impedir que se filtren pedidos de otros clientes. Para `CA-4.7`, guarda `key` en `idempotency_keys` con llave primaria y maneja la concurrencia para devolver el mismo `order_id` ante dos `POST /api/orders` simultáneos.

Para ver la estructura concreta de dependencias y pruebas, pasa a [la pista 3](3.md).
