# Pista 2. Verificación JWT con JWKS, autorización e idempotencia

Distingue siempre entre autenticación (`401 Unauthorized`, el token falta, venció o tiene firma inválida) y autorización (`403 Forbidden`, el usuario está autenticado pero intenta ver una orden que pertenece a otro `sub`).

Al validar JWT según RFC 8725, fija explícitamente la lista blanca de algoritmos permitidos (por ejemplo `RS256` o `ES256`), verifica `iss`, `aud` y `exp`, y guarda las llaves públicas JWKS en caché con un TTL razonable para evitar una llamada de red en cada request.

Para `CA-4.6`, persiste la dupla `(user_id, idempotency_key)` con restricción `UNIQUE` junto al `order_id` creado y el hash del payload. Si llega un reintento con la misma llave y el mismo payload, devuelve la respuesta guardada sin ejecutar otro checkout.

Para ver la estructura concreta de dependencias y pruebas, pasa a [la pista 3](3.md).
